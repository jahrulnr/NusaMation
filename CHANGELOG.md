## [Unreleased]

## [0.3.0] - 2026-11-20

### Added

- **Telegram typing indicator and operator docs.** While a Telegram turn runs the adapter refreshes `sendChatAction` (`typing`) about every four seconds; the indicator stops on the final send, disconnect or shutdown and never creates a message. `assets/docs/telegram.md` now ships with the embedded ops docs (token, settings, delivery, media, menus, troubleshooting), and the workspace ops pointer lists it.
- **Telegram HTML replies and attachments.** Outgoing text now uses `parse_mode: HTML` after one sanitizer (`<b>`, `<i>`, `<u>`, `<s>`, `<code>`, `<pre>`, `<blockquote>`, `<a href>` with http/https only); unknown tags become escaped text, tags inside `code`/`pre` stay literal, an unclosed tag is closed, and a parser rejection resends the original text unparsed so a formatting mistake never drops the message. `ResponseRules` names the rendered tags instead of promising plain text, and command replies, `/help` and approval pings share the same path. Replies may attach `[name](path)` / `![name](path)` files — the chat layer collects them and Telegram uploads them as multipart, choosing `sendPhoto` (≤10 MB; larger images become documents), `sendAnimation`, `sendVideo`, `sendVoice`/`sendAudio` and `sendDocument`, with sanitized captions capped at 1,024 characters. Inbound photo/document/video/audio/voice/video_note/animation/sticker downloads through `getFile` (20 MB ceiling, WhatsApp-style failure markers, webp stickers, token-redacted errors), and an album's items arrive as one turn after a 400 ms debounce with at most six attachments.
- **Telegram channel (slice 1): a private bot that answers chats over long polling.** New `internal/channels/telegram` adapter talks to the Bot API through a thin stdlib HTTP client (no library). The @BotFather token is stored sealed and never leaves `Settings()` — only `tokenSet` — and a new token is verified with `getMe` before saving. **Connect** validates the token, publishes the fixed 12-command `/` menu via `setMyCommands` once, then runs one `getUpdates` long-poll loop with a persisted offset (`channel.telegram.offset`), so a restart does not replay updates. Edits, channel posts and callback queries are ignored, and channel-type chats are skipped. Inbound mapping keeps `message_thread_id` both ways so forum topics stay separate, and message ids are stored as `chat_id:message_id` since Telegram ids are only unique per chat. The allowlist mirrors WhatsApp — empty denies everyone, a lone `*` in the user list allows every sender — with group policy `disabled`/`mention`/`all` on top, a bounded blocked-sender ring with Allow/Allow-group actions by numeric id (never username), and a two-hour staleness drop. Replies are one `sendMessage` per finished turn, capped at 4,096 characters. Control goes through the generic `/api/channels/telegram/*` endpoints; the settings screen lives under Channels as a second card. Disabled at boot with `-no-telegram`/`NUSAMATION_NO_TELEGRAM`.
- **Telegram session commands and room mentions.** A linked chat's `/` menu keeps the fixed 12 commands and appends the ACP session's commands (`setMyCommands` scope `chat`; names outside `^[a-z0-9_]{1,32}$` are skipped; 100 total). An empty session list, and `/new`, delete that scope so the default menu returns. Typing `@botusername` — after `/setinline` in BotFather — offers rooms and projects; the inserted `@handle` comes back as a `via_bot` message and becomes a conversation or project reference, including under the group mention policy. `#`, and file, folder, skill and MCP search, stay on the web composer.
- **Identity-mismatch warning on conversation control.** An agent process that hosts several rooms can route a session's conversation tools through another room's connection — the observed incident: a hunter room's agent believed its identity was the fixer room ("MCP refused self-send") because its `nusamation_conversation` calls resolved to the fixer's token. `list` and `send` now attach a `warning` when the caller room is idle while its agent runs a turn in another room, and the tool descriptions plus the agent docs tell agents to verify the `isSelf` row before relaying. The root fix belongs to the agent side (per-session MCP scoping); this makes the state visible and stops wrong-identity relays without breaking idle CLI callers.
- **Room labels and @mentions.** Every conversation gets a short lowercase handle — an animal (`cat`, `tiger`, …) auto-assigned at creation, unique across rooms; pre-existing rooms are backfilled at startup, oldest first, so your existing hunter/fixer rooms get `cat` and `dog`. Rename from the conversation menu (**Set label**, `PATCH /api/conversations/{id}` with `label`). The composer's `@` picker now offers rooms by label and projects by name — selecting one sends the prompt with a selected-references note carrying the exact conversation/project id, so "cek si @cat deh" is resolvable by the agent in one step. `list` rows carry the label, and the control tools `read`/`wait`/`send`/`stop` accept a conversation id **or its label** (`@cat` works from every agent's MCP child).
- Group allowlist as a picker: new `allowedGroups` setting holds full `…@g.us` JIDs, and the web panel's **Group allowlist** section lists every joined group by name with an Add/Remove toggle — each tap saves immediately, replacing the copy-a-JID-into-the-textarea step. The picker auto-loads when the account is linked; a group that was allowed but has been left keeps a remove row. `whatsapp set --groups/--group-add/--group-remove` mirrors it in the CLI, bare digits are refused as group entries (ambiguous with phone numbers), `*` may not be mixed with groups, and legacy stripped-group entries in `allowedNumbers` keep working. Blocked group traffic gains an **Allow group** action — allowing the member's number only opens their private chat. `GET /api/channels/whatsapp/groups` now reports each group's allow state.
- Outbound send pacing, per chat: `sendPacing` (seconds, default 5, 0–60) is the minimum gap between two messages to the same chat, and `queueCap` (default 20, 1–200) bounds the per-chat FIFO queue. Faster messages wait in the queue instead of being dropped or burst-sent — the WhatsApp-facing cadence now looks human. Both are editable in the web panel (Behaviour → Send pacing / Queue limit) and via `whatsapp set --send-pacing / --queue-cap`.
- Automation job cards gain **Run now** (one immediate run; the schedule is untouched, so the next cron occurrence still fires) and **Test send** (pings the result chat so a misconfigured channel or target is discovered immediately), with `POST /api/automations/{id}/run` and `/test-notify` behind them.
- WhatsApp now reports messages it cannot decrypt (`events.UndecryptableMessage`) at info level with sender and chat, instead of dropping them without a trace.
- WhatsApp blocked-sender list: recent senders the allowlist rejected are shown in the web panel with a one-tap **Allow** button.
- `nusamation whatsapp groups` and `GET /api/channels/whatsapp/groups` list joined groups (JID + name) so allowlist entries no longer have to be hunted for; the web panel has a **Load groups** helper.
- WhatsApp message index upgrades (migration 0012): an FTS5 search index with Unicode case-folding and a substring fallback, a per-message delivered/read `receipt` state from incoming receipts, and a tombstone that wipes text from a message deleted for everyone instead of leaving it searchable.
- Retention for the WhatsApp index: `--retention-days` / the `retentionDays` setting purges messages older than N days (default keeps everything).
- `whatsapp send` types `edit` and `revoke` update or delete one of the bot's own messages, keeping the index in sync; oversized media files are size-checked before being read.
- Group replies @mention the message author, and votes on approval polls survive a restart: a tap on a request that already ended answers "That request has already ended." instead of vanishing, while other participants' votes in a group no longer broadcast a guard message into the room.
- A full WhatsApp intake queue now tells an allowed sender the assistant is busy instead of dropping the message silently, and gating runs before a slot is taken.
- Automations can deliver each run's final answer to a chat channel (`--notify-channel`/`--notify-target`, plus form fields). The run's turn is submitted with that chat as its origin and delivered through the standard one-message machinery; no channel link is created, so an automation chat can never steal a link from another conversation, and approvals raised by an unattended run stay in the web inbox (migration 0013).

### Changed

- **Telegram token, allowlist and length corrections.** Saving a different bot token while connected cancels the old poll flow and starts a new one immediately (chat-menu fingerprints reset), instead of leaving the replaced token polling until a restart. A positive id in the group allowlist is refused by the settings API and dropped from stored legacy settings — a private chat's `chat_id` equals the user id, so it silently opened that DM. Replies and media captions are measured in UTF-16 code units (Telegram's own limit; an astral emoji counts as two) at the send boundary. The web panel disables group-allow actions while the `*` wildcard is active, and **Allow everyone** confirms and clears the group list in the same save. Telegram action errors now say only duplicates were removed from a saved user list, a failed save keeps the typed draft, the channel card's status dot follows `connected` instead of the sticky `loggedIn` flag, and Channels/About name a disabled Telegram adapter.
- **Retry sends a neutral `continue`, anchored to the failed turn.** The retry button previously re-queued the *last user message* — clicking Retry on an old error card re-sent whatever the newest prompt was (an unrelated request), and re-sending the original prompt made the agent redo work and risk duplicating side effects. `POST /api/conversations/{id}/retry` now takes `{turnId}` (every error card carries its failed turn), validates it belongs to the room and ended in error, and queues a fresh `continue` user message; completed or foreign turns are refused. The WhatsApp `/retry` command retries the newest failed turn the same way. The composer no longer clobbers a just-started retried turn with its queued snapshot — the socket's `turn.started` wins, so the Send button flips to Stop correctly.
- Composer prefixes now have one job each: `/` commands the session (slash commands, files, folders, skills, MCP servers), `@` is purely for mentions (rooms by label, projects by name — no file results mixed in), and `#` is parked — it triggers nothing until a use is decided. Mention typing also skips the server reference search entirely, so `@` no longer fires a request per keystroke. Existing `#`-labeled references in drafts and history still render; they just can't be newly picked.
- **Control center is a page, not a modal.** Settings now opens as a full view inside the main column instead of a dialog: the chat stays mounted behind it (transcript, scroll and draft untouched), Escape and the back button walk out level by level, and on narrow screens it becomes a two-level flow — section list first, section content pushed on top — instead of the cramped horizontal icon strip. Channel settings moved one level deeper: the Channels tab lists channel cards (WhatsApp) that open their own screen, so the QR poller and group load only run while that screen is open. Confirm and prompt dialogs now stack above the page instead of replacing it, so Cancel lands back on the list that opened them; selecting or starting a conversation leaves the page.
- WhatsApp honours the documented one-message-per-turn contract in code: interim assistant blocks (triggered by tool calls, thoughts or new agent message ids) no longer leave the channel while the turn runs. The segment-delivery interface is gone from the chat layer.
- WhatsApp reply truncation now matches the rule the agent is told: the delivery declares its own 30,000-character limit (`channels.TextLimiter`) and truncation counts runes, not bytes, so a multibyte reply is no longer cut shorter than promised. Channels without a declared limit keep the 3,500-character default.
- WhatsApp allowlist semantics: an **empty allowlist now denies everyone** — the agent stays silent until the operator explicitly adds a number or the wildcard `*` (allow everyone, which must be the only entry; `*` combined with numbers is refused by the CLI and the web). Previously an empty list allowed anyone, so a forgotten form meant a public agent. Recent blocked senders remain visible in the panel with a one-tap **Allow** action.

### Removed

- The conversation-control guard that denied `send`/`spawn`/`read`/`stop` to a turn started by another conversation. Agents working as a team can now relay results and delegate follow-up work through the bridge during delegated turns. What still bounds it: the caller token scopes every call, self-targeting stays refused, cross-conversation writes stay rate-limited, spawn stays capped at ten active children, and report stays one ping per minute.

### Fixed

- **One MCP child per room for directory-scoped harnesses.** OpenCode registers MCP servers from `session/new` per working directory, not per ACP session, so every room in the same project reused the first room's `nusamation_conversation` and `browser_use` child — and that child's bearer token. A relay from the second room could be refused as `target_self` while `list` reported the first room as `isSelf`. Injected server names now carry the room label (`nusamation_conversation_eagle`, `browser_use_eagle`; an unlabeled room falls back to its conversation id), so the harness launches a separate child with the right environment and token. Existing sessions adopt the new names on their next session load; a running agent process keeps old children until it is reloaded or restarted. The identity warning remains for harnesses that still share by command.
- **Telegram allowlist rejection could deadlock the whole channel.** `recordBlocked` published channel status while holding the blocked-ring mutex, and `publish` → `status` reads that same ring — a non-reentrant lock, so the first rejected sender (an empty allowlist means the first DM) froze the poll loop, status and every send. The ring lock is released before publish, and `status` reads the blocked list before taking the channel mutex. A regression test uses a real channel manager with a two-second timeout.
- **Telegram reconnect ownership.** A fast Disconnect→Connect could start flow B and then have flow A's cleanup clear B's client, polling flag and status, leaving a live poll loop reporting "disconnected". Each flow now carries a generation; only the current owner clears state. Replacing a token uses the same mechanism.
- **Telegram 429 handling and session menus.** `retry_after` is parsed and honored (polling waits instead of counting a failure; a small send hint retries once within the caller's deadline). Session commands whose description is shorter than Telegram's 3-character minimum are skipped so one entry cannot fail the whole menu. Logout and token replacement reset the per-chat menu fingerprints.
- **Telegram mention and blocked-ring hygiene.** A literal `@botname` now needs a whole-username boundary (`@nusa_bot_extra` and `x@nusa_bot` no longer count), and the two-hour staleness check runs before the allowlist so an old stranger message is not published into the blocked list.
- **Telegram settings and uploads.** Non-secret settings are persisted before a new token, so a failed settings write cannot leave the new token active while the caller sees an error. Upload file names have control characters removed and are length-bounded, so an agent label cannot inject multipart headers. Download errors stay token-redacted.
- **Refuse agents that reuse one ACP session id across conversations.** `registerACP` used to overwrite the notification routing silently: an agent backend that hands a second room the same session id (Devin-style "attach the latest cloud session" instead of starting fresh) would interleave both rooms' prompts into one agent context and reroute all notifications to the last registrant — with no log line. The ensure now refuses with `SessionReuseError` ("…which conversation X already owns; refusing to share one agent session between rooms — reset this room's session or reconnect the agent"), keeps the original owner's routing intact, and warns in the log with both conversation ids. The fake ACP test agent now mints unique ids per `session/new` like a real agent (honest mode) and pins one id under `FAKE_ACP_REUSE_SESSION` (dishonest mode) so the refusal is covered by tests: distinct per-room assignment, refusal text naming the owner, and the owner still completing follow-up turns after the refusal.
- A prompt sent by another conversation via the conversation-control bridge (`send`/`spawn`, channel `agent`) is now authored as **Agent** in the web transcript instead of masquerading as "You" — "You" is the human reading the room.
- `UpdateSettings` no longer mutates the live allowlist when a save is refused: the patch struct shared the slice backing array with the stored settings, so `json.Unmarshal` overwrote it in place even on the error path.
- Automation result delivery no longer moves a WhatsApp chat between conversations: the notify target is a delivery target, not a routing link. Previously `MoveChannelLink` reassigned the chat's link to the newest run (reproduced: an isolated run stole the chat from the operator's daily conversation and renamed it).
- Approvals and agent questions (elicitations) raised by an automation run are web-only and can no longer be answered from a linked chat: unattended turns record no origin sender, so the voter guard now denies them instead of falling open, and the result chat is no longer sent a question it cannot answer.
- Mirrored final answers now honor the receiving channel's declared reply limit (WhatsApp's 30,000 characters) instead of a fixed 3,000-byte cut, and a failed mirror surfaces as a web notice.
- An automation notify target without a channel — or a channel without a target — is refused with a clear error instead of silently dropping one side, and bare phone numbers are normalized to full user JIDs.
- Saving a WhatsApp allowlist from the web whose entries are all invalid is now refused with an error, like the CLI, instead of normalising to an empty deny-everything list by accident. The success toast reports the normalised entry count.
- A failed final WhatsApp send now surfaces as an error notice in the web conversation instead of disappearing into the log.
- Messages from non-allowlisted senders are logged at info level instead of debug, and the log line names both sender and chat.
- The WhatsApp settings panel no longer blames `NUSAMATION_NO_WHATSAPP` when the channel failed to start for another reason (for example an unreadable WhatsApp database).

### Known limitations

- `inbound_messages` keeps one dedupe row per inbound message and is never pruned. This is platform-wide (not Telegram-specific), so a long-running bot accumulates rows indefinitely.
- Telegram media and album downloads run inline in the poll loop: a ten-photo album on a slow link delays the next `getUpdates` until those transfers finish.
